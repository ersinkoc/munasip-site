Two planes, one phone system

The media plane is Asterisk 22 with PJSIP, ARI and AMI. The control plane is a Node/Fastify API that writes Asterisk configuration and executes IVR graphs. Employees and administrators use the React web application.

Follow a call

  1. A SIP provider or phone reaches Asterisk using the configured transport and media ports.
  2. Inbound routes select a destination: extension, ring group, queue, IVR, schedule or another supported target.
  3. The API’s ARI flow engine runs the published IVR graph. Nodes can play prompts, collect digits, query an API and select a destination.
  4. Asterisk handles the connected media and configured MixMonitor recording.
  5. AMI/ARI events feed live status and logs through the API. WebSocket updates reach the panel and portal.

The browser softphone registers over WSS through /asterisk-ws. WebRTC media uses DTLS-SRTP; coturn supports off-site media traversal.

Persistence is part of the architecture

The single image uses /data for the embedded database, settings, secrets, Asterisk configuration and recordings. With Compose, named volumes include pgdata, recordings, uploads and asterisk_config; certificates are bind-mounted.

A volume is persistence, not a backup. Plan database exports, recording archives and recovery of encryption keys. Test restores separately from an ordinary application restart.

Know the boundaries

MunaSIP targets a small office around 20 extensions. It is not a documented automatic high-availability cluster. Carrier-side failover can redirect inbound calls if the PBX host or uplink fails.

The documented scope does not include video meetings, team chat, WhatsApp, predictive dialing or first-party desktop/mobile apps. Integrate external tools through the API and webhooks where appropriate.
